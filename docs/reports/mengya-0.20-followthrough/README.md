# MengYa 0.20 · Conversational Follow-through

基线 `0.19.1-morrow`；本包 `0.20-morrow` / versionCode 28；数据库 v17。

## 已实现

### 小计划数据模型（持久化，不靠提示词记忆）
- `small_plans`：id、内容、时间范围、关联目标、状态（ACTIVE/COMPLETED/PAUSED/CANCELLED）、来源消息 id、创建/更新时间。
- `plan_events`：每次状态变更追加一条事件，保留历史，不覆盖原始记录。
- 唯一写入口 `SmallPlanRepository`；计划不写入进展表、不建立第二套目标系统。
- v17 迁移：新增两张表 + `record_proposals.plan_change_json / applied_plan_id`。

### RecordProposal 扩展 PLAN
- `PlanChangeKind.CREATE / STATUS`；草稿存同一张候选表。
- 创建：内容、时间范围（用户原话）、可选关联目标；不编造截止日期/频率。
- 状态：只能引用已有计划 id，更新为完成/暂停/取消/恢复。
- 闸门区分：未来意向（准备/打算/计划）→ 计划；已完成事实（练了/昨天）→ 进展；“有点想学” → 普通聊天。
- 卡片：待确认可“记下这个计划 / 修改 / 放弃”；状态变更可“确认更新”；已确认折叠为一行。
- 写入服务 `PlanRecordApplyService`：事务内创建/改状态并原子迁移候选；重复点击幂等。

### 上下文
- 已授权「目标」类别时，顾问上下文包含最近的小计划与状态（`[小计划#id] 内容（状态，时间）`），用于后续跟进与回顾；未授权不读取。

## 真机结果（未达标）

真实 `deepseek-flash` 两次尝试：
1. “这周我准备练三次吉他。” → 顾问正常讨论，**没有生成小计划卡**。
2. “帮我把「这周练三次吉他」记成一个小计划。” → 模型仍要求补充“具体哪几天、每次多久”，返回 `record:null`，**没有生成草稿**。

随后放宽提取提示词（明确要求记计划时允许信息不全），但第三次注入未成功送达，未获得卡片截图。

因此以下验收**未完成**：确认写入、重启后计划存在、后续状态更新、周回顾引用计划、取消后不写入、多计划歧义。

## 单元测试
- **336 项通过，0 失败**；新增 PLAN 解析、状态更新、闸门区分、null 场景 4 项。
- `assembleDebug` / `assembleQa` 成功。

## 已知问题 / 原因
1. 真实模型倾向于先追问计划细节，未按提示词直接产出 JSON 草稿；需要更强约束或改为“先记下最小信息、再补充”的两步交互。
2. 计划提取没有在真实设备上走通确认与持久化，因而没有录屏与重启证据。
3. 计划未纳入备份 v2（新增表），恢复旧备份后计划不会迁移。
4. 多候选计划的澄清目前只靠提示词要求返回 null，客户端没有候选选择 UI。
5. 状态更新（暂停/取消）与进展记录的边界未真机验证。

## 结论
本轮完成了可持久化的小计划模型、状态历史、提案与写入通道，但**真实模型端到端闭环未打通**，不能宣称 0.20 的“约好一件事→隔几天接上”已完成。
